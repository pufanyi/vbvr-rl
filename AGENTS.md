## Model And Training

- `WanI2VForTraining` is the central model wrapper. It reads `boundary_ratio` from `model_index.json`, `flow_shift` from the scheduler config, builds the shifted sigma/timestep schedule, and routes A14B timesteps to high (`transformer`) or low (`transformer_2`) experts. 5B TI2V is a dense single-transformer model with expanded per-token timesteps.
- `src.cli.train_i2v` dispatches `SFTConfig.trainer: i2v` to `I2VTrainer` and `trainer: cos` to `COSTrainer`; `src.cli.train_i2v_correction` uses `CorrectionConfig`; `src.cli.train_grpo` uses `RLConfig` and `DanceGRPOTrainer`.
- SFT and RL use separate base stacks (`BaseTrainer` and `BaseRLTrainer`) with duplicated distributed/model/dataset/FSDP/checkpoint logic. Fixes to FSDP, HSDP, dataloading, checkpointing, or resume semantics often need to be mirrored in both stacks.
- Full fine-tuning loads trainable transformers in fp32 by default when `transformer_load_dtype: auto`; LoRA base weights stay bf16 unless overridden. If `param_dtype: bfloat16` with fp32 transformer load, gradient checkpoint recompute uses bf16 autocast.
- Keep that fp32-load/bf16-recompute checkpoint path compatible with `torch.compile` by entering autocast around non-reentrant `checkpoint()` and letting PyTorch capture the ambient autocast state. Do not restore the former nested autocast `context_fn`: PyTorch 2.11 Dynamo rejects it because compiled checkpoint contexts must be `TorchDispatchMode` instances.
- `disable_cudnn_sdp` defaults true because cuDNN SDPA backward has produced NaNs for Wan low-noise training on H100/PyTorch 2.11. A 2026-08-03 H800 stress covered random BF16 forward/backward at sequence lengths 5,376, 10,496, and 21,504 plus one real 5B 512x512x81/T30/VBVR/compile optimizer step without a NaN, but this limited H800 result does not invalidate the model/data-dependent H100 failure. Be explicit before changing attention backend behavior.
- The Fujian 5B 512x512x81 production path pins Liger 0.8.1, `kernels` 0.16.0, Transformers 5.14.1, `_flash_3_hub`, and Inductor. Wan TI2V-5B has 120 safe Liger replacements, all Q/K RMSNorms; the production-shape BF16 RMSNorm microbenchmark improved about 8%. Do not substitute Liger FFN/LayerNorm/RoPE kernels: Wan uses approximate GELU, explicit FP32 LayerNorm, and custom 3D RoPE. Optional Liger cuTile was effectively tied with default Triton and CuTe DSL was slower on H800, so neither belongs in the environment. Exact batch-8 attention forward+backward medians favored FA3 over native cuDNN and native Flash for both self and cross attention; keep FA3 explicit and cuDNN disabled in production.
- Expert parallel splits the world into high/low expert groups and requires `fsdp=true`, `train_experts: both`, even world size, and synchronized control flow. `expert_parallel_data_mode: duplicate` makes expert groups see the same data stream; `split` shards data across all ranks for full global throughput.
- FSDP2 requires all ranks to execute compatible wrapped-module forward sequences. Keep timestep sampling and DanceGRPO replay timestep selection rank-synchronized; per-rank divergence in high/low routing can hang NCCL/FSDP collectives.
- COS supports N-step paths `linear`, `target_cosine`, and `target_sigmoid`; legacy paths are 2-step only. `len(cos_tau_sigma)` must equal `len(video_latents) - 1`, and latent COS datasets must be generated with all chain latents.
- Correction training is supervised correction, not policy gradient. It currently forbids expert parallel; use EMA for the teacher rollout unless intentionally testing live-student correction.

## DanceGRPO And Rewards

- DanceGRPO requires `grpo_group_size >= 2`, `grpo_num_sampling_steps >= 2`, and either a positive fixed `grpo_sde_noise_scale` or a valid Flow-CPS random range. It does not support expert parallel.
- For stochastic `neg_loss` smoke runs, do not put each group member in a separate one-sample reward chunk: reward evaluation preserves and restores torch RNG, so repeated one-sample calls can receive identical randomness and yield zero group advantages. Batch at least two group members together and use `scripts/dev/validate_grpo_parameter_update.py` to prove a nonzero optimizer update.
- Flow-CPS can set `grpo_cps_noise_scale_range: [min, max]` to sample one uniform coefficient per prompt/GRPO group and optimizer step. All `G` rollouts in that prompt group share the value; shared-prompt and split actors reproduce it deterministically, and replay must use the coefficient stored with the rollout. Omitting the range preserves fixed `grpo_sde_noise_scale` behavior.
- Treat arXiv `2509.05952v4` (2025-12-08) as the current Flow-CPS paper. It fixes the v1 positive-sign typo and explicitly defines the training surrogate as negative squared error with the `2 * sigma**2` denominator removed; the official `IamCreateAI/FlowCPS` implementation at commit `814c359...` then averages that elementwise error over every non-batch dimension, matching Wan-Trainer's dimension-mean negative-MSE log-prob and mean-MSE reference penalty. The official online evaluation calls the same patched FlowMatch-Euler/CPS pipeline with `noise_level=0`, so under an identical sigma grid and CFG its deterministic boundary is first-order Euler. Do not compare it with a different solver/grid/CFG and attribute the resulting gap to CPS alone.
- Unified ODE/SDE/CPS `save_steps` galleries show the post-CFG predicted-clean endpoint `x0 = x_sigma - sigma * velocity`, not the noisy sampler state. For 5B `expand_timesteps` I2V, every preview must re-pin latent frame zero to the encoded input condition because the real rollout discards the transformer's frame-zero velocity. Human-facing labels are one-based and include the source sigma; compatibility filenames remain zero-based. The last gallery cell decodes the actual `final_latent` at sigma zero, and `manifest.json` records each cell's kind and source/output sigma.
- Non-split `grpo_shared_prompt_batch=true` means every rank reads the same global prompt batch and shards each prompt's `grpo_group_size` samples across ranks. `batch_size` is the global optimizer-step prompt count. By default it must divide `world_size`; when `grpo_shared_prompt_microbatch_size` is set, that wave size must divide both `batch_size` and the data-parallel world, and the ranks per prompt must divide `grpo_group_size`.
- Raw shared-prompt GRPO leaves the physical `I2VDataset` order unchanged when `shuffle_raw_indices=false`, then applies `DistributedSampler(num_replicas=1, rank=0, shuffle=True, seed=cfg.seed)`: every rank sees the same deterministic global permutation, and `sampler.set_epoch(epoch)` produces a new permutation each epoch. The current 50k manifest configs therefore shuffle at sampling time even though their manifest-backed dataset remains task-grouped. Beware `auto_resume: true` combined with `reset_dataloader: true`: loading the latest checkpoint is weight-only initialization that resets optimizer/step/epoch/batch to zero, so a restart repeats the exact epoch-0 permutation instead of continuing the saved dataloader position.
- Shared-prompt prompt waves prepare every wave before any replay, then replay them into one optimizer update. This lets later CPU rewards overlap earlier replay without making trajectories one policy update stale. For bs32/G32, wave16 gives 2 ranks x 16 rollouts per prompt at world32 and 4 ranks x 8 at world64; at world128, wave32 gives 4 ranks x 8 rollouts per prompt in one wave. The Fujian 512x512x81 world128 config uses that wave32 layout with rollout/replay chunks capped at 8, reducing each rank from two batch-4 replay chunks to one batch-8 chunk without changing global batch/G semantics. A 2026-07-25 world32 trace of the old single-wave path averaged about 44% GPU utilization with median zero and about 53% idle samples: replay was stable around 180-195 seconds, while reward/barrier tails varied from about 60 to 1140 seconds and were strongly associated with EasyOCR-heavy O-34 prompts. The 2026-08-03 eight-H800 batch-2 validation preserves the world128 per-rank layout of four ranks per prompt and eight rollouts/rank, and completed three production-shape optimizer steps; the 16-node HSDP topology remains unvalidated.
- On the current non-split standard/shared-prompt DanceGRPO paths, `grpo_train_sample_batch_size` does not independently re-chunk stored trajectories; replay reuses the rollout chunks made by `grpo_sample_batch_size`. Do not assume a configured replay micro-batch of 1 is effective until this path is fixed or the rollout micro-batch is also 1.
- FSDP2 `set_requires_gradient_sync(false)` is a severe full-finetune memory trap because it accumulates full unsharded gradients. An 8x80GB H100 A14B two-expert smoke at 256x256x161 reproducibly reached about 81,194 MiB and OOMed when an unsynchronized high-expert gradient remained resident during low-expert backward, even at micro-batch 1 and with T5 offloaded. Forcing reduce-scatter on every backward completed the same real raw-data/T5/VAE/VBVR-reward/high+low/AdamW step at a measured 44,464 MiB peak. Full-finetune replay must sync each backward for the safe implementation, or reorder replay expert-major and reduce-scatter before switching experts; validate the optimized form for gradient equivalence and run a production-T/G one-step smoke before launch.
- Single-node full-A14B DanceGRPO supports `tensor_parallel_size: 2` composed with four FSDP data replicas on eight GPUs. TP is applied before FSDP2, shards Wan attention/FFN projections, and preserves the original global-across-head Q/K RMSNorm with an autograd-aware TP all-reduce. TP pairs share sampler shards and rollout RNG; VAE/CPU rewards run only on TP rank 0 and broadcast, while policy-forward rewards run collectively. The current implementation is RL-only, requires `fsdp: true` and `hsdp: false`, and rejects LoRA, expert parallel, split RL, and trainable text encoders. It accepts Liger plus `torch.compile`: all current Wan Liger RMSNorms are converted to the collective-aware TP norm (so Liger provides compatibility rather than a fused-norm speedup), and that norm is kept as an eager Dynamo boundary because compiling through its `distributed.nn` collective silently produced wrong gradients. Compile modules in place to preserve DCP keys. Fresh Inductor/Triton builds require a host C compiler and matching Python development headers. `scripts/lib/env.fish` exports a valid explicit/system/CPATH include or reuses an already-installed same-major/minor uv Python header directory without downloading; `scripts/train/grpo_multinode.fish` preflights the Triton CUDA driver on every node before loading the model. Prefer installing the exact `python3.12-dev` package in production images.
- Runtime-only cluster images can provision same-major/minor Python headers once with `scripts/dev/bootstrap_triton_python_headers.fish`; it installs an ignored shared uv toolchain under `storage/toolchains/uv-python` and proves a fresh-cache Triton driver build. `scripts/lib/env.fish` discovers that versioned include directory on every node without downloading at launch. Multi-node GRPO defaults `TRITON_CACHE_DIR` to node-local `/tmp/wan-trainer-triton-cache`; set `WAN_TRAINER_TRITON_PREFLIGHT_ONLY=1` for an all-node compiler/header check that exits before `torchrun`, then remove it for the real launch. Downloaded Hub kernels instead persist under `~/.cache/wan-trainer/kernels`. FA3 is pinned to revision `43f0bd269777115d94ff826e0d113ce9c1c9087b` and loaded through `kernels.load_kernel`, so compute ranks make no Hub publisher/version requests; prefetch its 798,352,256-byte CUDA 12.6 artifact once from a networked login node with `src.cli.prefetch_attention_kernel`. GRPO launchers deliberately replace an ambient `KERNELS_CACHE` because scheduler images may inject an ephemeral `/tmp` value; use `WAN_TRAINER_KERNELS_CACHE` only for an intentional persistent override. Root-launched jobs resolve `~` to `/root`, so bake the cache into `/root/.cache/wan-trainer/kernels` before saving the image or point that override at the shared `/mnt/umm/users/pufanyi/.cache/wan-trainer/kernels` path on every node. An exact system `python3.12-dev` package remains the preferred production-image fix.
