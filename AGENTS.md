## Repository Shape

- Wan-Trainer is a research training stack for Wan2.2 I2V/TI2V Diffusers models. It supports SFT, COS path training, on-policy correction, DanceGRPO-style RL, latent WebDataset training, DCP checkpointing, LoRA extraction/loading, and VBVR/maze evaluation.
- Start with `docs/README.md` for architecture-level context. The main source map is: `src/cli/` entry points, `src/models/` Wan model wrapper and COS paths, `src/data/` raw/latent datasets and remote I/O, `src/trainer/` SFT/RL trainers, rewards, FSDP/DCP runtime, `src/precompute/` latent and synthetic data builders, `src/eval/` VBVR/maze scoring helpers, `scripts/` fish launchers/operator utilities, `configs/` runnable experiment configs, `tests/` focused unit/consistency checks.
- Most fish launchers source `scripts/lib/env.fish`, change to the repo root, activate `.venv`, and set `PYTHONPATH`. When running Python inside this project, prefer direct `.venv/bin/python` or `.venv/bin/torchrun` commands; do not default to `uv run`.
- Generated/heavy local artifacts belong under ignored paths such as `storage/`, `wandb/`, `logs/`, `tmp/`, and `data/diffsynth_mix/`. Do not commit generated latent shards or local dataset caches.

## Data Contracts

- Raw I2V data is configured by a JSON file pointing to one or more Parquet files, not by a flat list of samples. Rows use `videos` for ordered COS/multi-step chains or `video` for a single target, plus `prompt` and optional `image`; absent `image` falls back to the first frame of the final video.
- Raw media paths can be local or `s3://`. S3 localization goes through `src/data/remote_io.py` and the vendored `aoss/` client. Credentials/config are environment-driven: `WAN_TRAINER_AOSS_CONF_RULES`, `WAN_TRAINER_AOSS_CONF_PATH`, and `WAN_TRAINER_REMOTE_CACHE_DIR`.
- For remote raw training, `raw_remote_prefetch_lookahead`, `raw_remote_prefetch_workers`, `WAN_TRAINER_DECORD_NUM_THREADS=1`, and `dataloader_in_order=false` are practical knobs. The DiffSynth mix launcher `scripts/train/i2v_diffsynth_mix_260603_multinode.fish` records the current AOSS/cache defaults.
- Remote raw media cache locks are bounded by `WAN_TRAINER_REMOTE_LOCK_TIMEOUT_SECONDS` and `WAN_TRAINER_REMOTE_LOCK_STALE_SECONDS`; old `.lock` directories in `WAN_TRAINER_REMOTE_CACHE_DIR` can otherwise look like random `DataLoader timed out` failures. Use `dataloader_item_trace_seconds` on raw I2V configs to dump worker stacks for slow `__getitem__` calls before the DataLoader timeout fires.
- Latent training uses WebDataset `shard-*.tar` files with `{key}.safetensors` and `{key}.json`. Required tensors are `prompt_embeds`, `condition`, and either `latents` or COS-style `latents_0`, `latents_1`, ...; extra tensors such as `maze_*` are passed through for rewards.
- Always set `dataset_size` for latent/WebDataset configs. Trainers derive per-rank epoch lengths from it; missing or wrong values can break LR scheduling or cause uneven-rank epoch endings.
- If shard count is smaller than rank count, `VBVRLatentDataset` falls back to sample-level splitting inside shard groups. This works, but resharding to at least the training world size gives better sequential I/O.
- 5B TI2V uses `expand_timesteps` and a different condition format from A14B I2V. Recompute latents/conditions with the same base model family used for training or evaluation.

## Model And Training

- `WanI2VForTraining` is the central model wrapper. It reads `boundary_ratio` from `model_index.json`, `flow_shift` from the scheduler config, builds the shifted sigma/timestep schedule, and routes A14B timesteps to high (`transformer`) or low (`transformer_2`) experts. 5B TI2V is a dense single-transformer model with expanded per-token timesteps.
- `src.cli.train_i2v` dispatches `SFTConfig.trainer: i2v` to `I2VTrainer` and `trainer: cos` to `COSTrainer`; `src.cli.train_i2v_correction` uses `CorrectionConfig`; `src.cli.train_grpo` uses `RLConfig` and `DanceGRPOTrainer`.
- SFT and RL use separate base stacks (`BaseTrainer` and `BaseRLTrainer`) with duplicated distributed/model/dataset/FSDP/checkpoint logic. Fixes to FSDP, HSDP, dataloading, checkpointing, or resume semantics often need to be mirrored in both stacks.
- Full fine-tuning loads trainable transformers in fp32 by default when `transformer_load_dtype: auto`; LoRA base weights stay bf16 unless overridden. If `param_dtype: bfloat16` with fp32 transformer load, gradient checkpoint recompute uses bf16 autocast.
- Keep that fp32-load/bf16-recompute checkpoint path compatible with `torch.compile` by entering autocast around non-reentrant `checkpoint()` and letting PyTorch capture the ambient autocast state. Do not restore the former nested autocast `context_fn`: PyTorch 2.11 Dynamo rejects it because compiled checkpoint contexts must be `TorchDispatchMode` instances.
- `disable_cudnn_sdp` defaults true because cuDNN SDPA backward has produced NaNs for Wan low-noise training on H100/PyTorch 2.11. Be explicit before changing attention backend behavior.
- Expert parallel splits the world into high/low expert groups and requires `fsdp=true`, `train_experts: both`, even world size, and synchronized control flow. `expert_parallel_data_mode: duplicate` makes expert groups see the same data stream; `split` shards data across all ranks for full global throughput.
- FSDP2 requires all ranks to execute compatible wrapped-module forward sequences. Keep timestep sampling and DanceGRPO replay timestep selection rank-synchronized; per-rank divergence in high/low routing can hang NCCL/FSDP collectives.
- COS supports N-step paths `linear`, `target_cosine`, and `target_sigmoid`; legacy paths are 2-step only. `len(cos_tau_sigma)` must equal `len(video_latents) - 1`, and latent COS datasets must be generated with all chain latents.
- Correction training is supervised correction, not policy gradient. It currently forbids expert parallel; use EMA for the teacher rollout unless intentionally testing live-student correction.

## DanceGRPO And Rewards

- DanceGRPO requires `grpo_group_size >= 2`, `grpo_num_sampling_steps >= 2`, and either a positive fixed `grpo_sde_noise_scale` or a valid Flow-CPS random range. It does not support expert parallel.
- Flow-CPS can set `grpo_cps_noise_scale_range: [min, max]` to sample one uniform coefficient per prompt/GRPO group and optimizer step. All `G` rollouts in that prompt group share the value; shared-prompt and split actors reproduce it deterministically, and replay must use the coefficient stored with the rollout. Omitting the range preserves fixed `grpo_sde_noise_scale` behavior.
- Non-split `grpo_shared_prompt_batch=true` means every rank reads the same global prompt batch and shards each prompt's `grpo_group_size` samples across ranks. `batch_size` is the global optimizer-step prompt count. By default it must divide `world_size`; when `grpo_shared_prompt_microbatch_size` is set, that wave size must divide both `batch_size` and the data-parallel world, and `grpo_group_size` must divide the ranks per prompt.
- Shared-prompt prompt waves prepare every wave before any replay, then replay them into one optimizer update. This lets later CPU rewards overlap earlier replay without making trajectories one policy update stale. For bs32/G32, wave16 gives 2 ranks x 16 rollouts per prompt at world32 and 4 ranks x 8 at world64. A 2026-07-25 world32 trace of the old single-wave path averaged about 44% GPU utilization with median zero and about 53% idle samples: replay was stable around 180-195 seconds, while reward/barrier tails varied from about 60 to 1140 seconds and were strongly associated with EasyOCR-heavy O-34 prompts. The prompt-wave path has CPU unit/static coverage but still needs a production-shape GPU optimizer-step smoke before being treated as launch-validated.
- On the current non-split standard/shared-prompt DanceGRPO paths, `grpo_train_sample_batch_size` does not independently re-chunk stored trajectories; replay reuses the rollout chunks made by `grpo_sample_batch_size`. Do not assume a configured replay micro-batch of 1 is effective until this path is fixed or the rollout micro-batch is also 1.
- FSDP2 `set_requires_gradient_sync(false)` is a severe full-finetune memory trap because it accumulates full unsharded gradients. An 8x80GB H100 A14B two-expert smoke at 256x256x161 reproducibly reached about 81,194 MiB and OOMed when an unsynchronized high-expert gradient remained resident during low-expert backward, even at micro-batch 1 and with T5 offloaded. Forcing reduce-scatter on every backward completed the same real raw-data/T5/VAE/VBVR-reward/high+low/AdamW step at a measured 44,464 MiB peak. Full-finetune replay must sync each backward for the safe implementation, or reorder replay expert-major and reduce-scatter before switching experts; validate the optimized form for gradient equivalence and run a production-T/G one-step smoke before launch.
- Single-node full-A14B DanceGRPO supports `tensor_parallel_size: 2` composed with four FSDP data replicas on eight GPUs. TP is applied before FSDP2, shards Wan attention/FFN projections, and preserves the original global-across-head Q/K RMSNorm with an autograd-aware TP all-reduce. TP pairs share sampler shards and rollout RNG; VAE/CPU rewards run only on TP rank 0 and broadcast, while policy-forward rewards run collectively. The current implementation is RL-only, requires `fsdp: true` and `hsdp: false`, and rejects LoRA, expert parallel, split RL, and trainable text encoders. It accepts Liger plus `torch.compile`: all current Wan Liger RMSNorms are converted to the collective-aware TP norm (so Liger provides compatibility rather than a fused-norm speedup), and that norm is kept as an eager Dynamo boundary because compiling through its `distributed.nn` collective silently produced wrong gradients. Compile modules in place to preserve DCP keys. Fresh Inductor/Triton builds require a host C compiler and matching Python development headers. `scripts/lib/env.fish` exports a valid explicit/system/CPATH include or reuses an already-installed same-major/minor uv Python header directory without downloading; `scripts/train/grpo_multinode.fish` preflights the Triton CUDA driver on every node before loading the model. Prefer installing the exact `python3.12-dev` package in production images.
- Runtime-only cluster images can provision same-major/minor Python headers once with `scripts/dev/bootstrap_triton_python_headers.fish`; it installs an ignored shared uv toolchain under `storage/toolchains/uv-python` and proves a fresh-cache Triton driver build. `scripts/lib/env.fish` discovers that versioned include directory on every node without downloading at launch. Multi-node GRPO defaults `TRITON_CACHE_DIR` to node-local `/tmp/wan-trainer-triton-cache`; set `WAN_TRAINER_TRITON_PREFLIGHT_ONLY=1` for an all-node compiler/header check that exits before `torchrun`, then remove it for the real launch. An exact system `python3.12-dev` package remains the preferred production-image fix.
- The runnable full-FT config is `configs/train_dancegrpo_vbvr_pro_a14b_256x256x161_rule_cps_from_sft_diffsynth_mix_260603_bs_16_lr_1e-5_full_tp2_fsdp4.yaml`. Its standard path uses local `batch_size: 4` over DP4 to preserve 16 global prompts, `G=16`, `T=30`, rollout/replay chunks of 1, `grpo_fsdp_sync_each_backward: true`, and `grpo_offload_inference_models: true`. A real 8x80GB H100 one-step run with raw T5/VAE, `vbvr_rule`, 17 replay timesteps, both experts, nonzero lr=1e-5, gradient clipping, and AdamW completed in 4,496.43 seconds with 59.4 GiB PyTorch allocated / 64.5 GiB reserved peak (about 69.1 GiB observed by `nvidia-smi`). - The four-node counterpart is `scripts/train/dancegrpo_vbvr_pro_a14b_full_tp2_4node.fish`. - On one 8-GPU node, `hsdp: true` intentionally falls back to plain FSDP. Without prompt waves, shared-prompt `batch_size: 16` is invalid at world size 8; use a wave size that divides 16 and fits world size 8, choose a smaller global batch, or use the TP standard-path configuration above to preserve a 16-prompt global batch as local batch 4 x DP4.
- Split RL is controlled by `rl_train_node_count` or `rl_train_rank_count`; train ranks come first, rollout actors are the remaining ranks. `rl_actor_weight_sync='lora'` requires LoRA, `full` currently requires `rl_async_rollout=true`, and `none` is only useful for plumbing/stale-actor smoke tests.
- Async split rollout keeps each optimizer step semantically unchanged but pre-generates future steps through a bounded queue. `rl_async_rollout_prefetch_steps: 0` auto-picks enough queued steps to keep rollout actors busy when `rollout_world_size > grpo_group_size`.
- The 64-GPU A14B VBVR-Pro LoRA-r32 run is configured by `configs/train_dancegrpo_vbvr_pro_a14b_256x256x161_rule_cps_from_sft_diffsynth_mix_260603_bs_32_lr_1e-5_lora_r32.yaml`. Keep the 32-prompt/G=32 global semantics while using rollout/replay micro-batches 2/1 for A14B memory, and use the LoRA learning rate 1e-5 with 100 warmup steps.
- Rewards are registered in `src/trainer/rewards/__init__.py`. Current names include `neg_loss`, `maze`, `maze_line`, `maze_tracker`, and `vbvr_rule`. Rewards with `requires_vae = True` force VAE loading even with precomputed latents.
- `vbvr_rule` is contract-locked to final VBVR-Pro `main_v2`: it shares the canonical decoded-tensor-to-uint8 conversion with inference, verifies the full scorer-source SHA-256, writes frames with Diffusers `export_to_video` exactly like CPS/ODE generation, runs the shared 1024x1024/all-frame/max-five-second preparation path (161 frames become 33 FPS), supplies prompt/`gt_path`/`metafile_path`, and calls the same `run_evaluation.evaluate_single_video` entrypoint. Scorer failures and invalid scores fail training by default instead of silently becoming zero.
- The scorer runs in spawned CPU processes with CUDA hidden so EasyOCR cannot allocate on the training GPUs. `vbvr_reward_cpu_workers` is the subprocess count per reward-producing rank, not a node-global count. Keep each node's total native-thread budget bounded: the 5B manifest-RL configs use two workers x eight threads per rank after a 50-task benchmark beat one x 16, while other standard configs may retain one x 16 per rank (or per TP pair). Keep `vbvr_reward_decode_batch_size: 8` for VAE throughput.
- VBVR reward execution is a bounded producer-consumer pipeline: after each VAE decode batch, samples are queued immediately for background video preparation and CPU scoring; DanceGRPO produces later rollout chunks before resolving reward handles in submission order. TP rank 0 remains the sole VAE/CPU producer and resolve preserves TP broadcast ordering. `vbvr_reward_max_pending_jobs: 0` auto-selects `max(decode_batch_size, 2 * cpu_workers)`. The prompt-wave DiffSynth manifest-RL configs use `16`, allowing two decoded size-8 batches (about 483 MiB/rank for 256x256x161 RGB) to remain in flight; keep the bound finite. Put disposable reward video temp directories on node-local `/tmp`: this workspace's `/mnt/umm` path is shared QuarkFS, whose metadata/I/O contention can extend scorer tails.
- Spawned reward workers import the training entrypoint before their initializer runs, so clearing `CUDA_VISIBLE_DEVICES` alone is insufficient after an earlier PyTorch CUDA probe: `torch.cuda.is_available()` can remain true while `device_count()` becomes zero, causing EasyOCR checkpoint loads to fail. CPU scorer initialization must also force CUDA availability false; preserve the regression that probes CUDA before applying worker isolation.

## Checkpoints And Conversion

- New training checkpoints use the unified DCP high/low layout under `checkpoint-N/high/` and `checkpoint-N/low/`, plus rank-local optimizer/dataloader files and optional PEFT LoRA sidecars. ## Development And Verification

- Run the project suite as `.venv/bin/python -m pytest tests`, not bare repository-root `pytest`: root discovery also collects the vendored `aoss/tests`, whose legacy top-level `common_util` imports are not valid in the project environment and can make collection slow before it fails.
- Use targeted tests for the touched surface. Useful CPU tests include `tests/test_cos_path.py`, `tests/test_dancegrpo_split.py`, `tests/test_i2v_trainer.py`, `tests/test_vbvr_latent_dataset.py`, and `tests/test_trainer_utils.py`.
- This repo's `.venv` may not have dev tools installed until needed. Install with `uv pip install --python .venv/bin/python <package>` when a missing local test tool blocks verification.
- `pyproject.toml` uses Python >=3.12, `uv.lock`, and Ruff line length 120. Keep reusable Python logic under `src/`; scripts should stay thin launchers or operator utilities.
- When adding a reward, create a `BaseReward` subclass, decorate it with `@register_reward("name")`, import the module in `src/trainer/rewards/__init__.py`, and set `grpo_reward_fn` in the YAML.
- When changing data schema, latent precompute, condition construction, checkpoint remapping, or distributed routing, add or update focused tests. These areas silently break expensive runs if only checked manually.
